# Bounded score-timing refit review

Sparse human score anchors can now produce a deterministic bounded refit preview between neighboring reviewed correspondences. A separate acceptance contract records the exact shared-timing candidate and exact bounded-refit preview that a human reviewed.

Acceptance is persisted at `review/score_timing_refit_acceptance.json`. The evidence contains the full reviewed candidate plus the full refit preview, including the recording, score, authority-track, and authority-output provenance already carried by those models. Loading current acceptance rebuilds the candidate and preview and rejects the evidence if either object has changed.

The acceptance write path revalidates the current candidate and preview while holding the score-mapping transaction lock. Score-anchor confirmation and manual score-beat marking use that same transaction lock for their complete read-modify-write operation. This serializes anchor evidence changes against refit acceptance, so acceptance cannot persist a preview built from one anchor set while a concurrent edit publishes another. If the candidate or preview changed after it was shown to the user, acceptance fails closed and the user must refresh and review again. This mirrors the existing exact-candidate promotion boundary and prevents a human from approving one timing proposal while a different proposal is persisted.

Song Workspace now builds the bounded preview automatically once at least two current human score anchors exist. The score-aware review strip reports the number of reviewed regions, the number of symbolic score beats covered, and the maximum absolute change from the automatic candidate. Short dashed ticks on the timeline show interior refit beat positions while filled human-anchor markers remain visually separate. Cursor guidance also reports the nearest bounded-refit score beat and its millisecond adjustment relative to the automatic candidate.

`Accept bounded refit review` requires an explicit confirmation dialog and passes the exact candidate and exact preview currently displayed to the acceptance contract. If either changes before persistence, the action fails closed. A current accepted preview disables the button and is labeled as human-reviewed; stale acceptance never authorizes the new preview and instead requires review again.

Current acceptance can materialize a read-only song-wide accepted score-timing map. Every symbolic score beat inside an accepted neighboring-anchor span receives the accepted bounded-refit timestamp, while every beat outside those human-reviewed bounds keeps the current automatic candidate timestamp unchanged. Human endpoints remain explicit, interior reviewed beats are distinguished from untouched candidate beats, and the materializer refuses to produce a map if the resulting recording times reverse or collapse at a reviewed boundary. Acceptance revalidation, authority-output loading, and the entire materialization pass are performed under the same score-mapping transaction lock, so concurrent score fan-out cannot replace the role-based authority JSON between provenance validation and beat-grid consumption.

The accepted map now has its own explicit promotion boundary. `promote_reviewed_score_timing()` rebuilds the current accepted map while holding the same score transaction and requires byte-for-byte model equality with the map supplied by the caller. Only then is `analysis/reviewed_score_timing.json` written as human-confirmed song-level timing authority. Loading that authority rebuilds the current accepted map under lock and rejects the persisted artifact when the underlying accepted evidence changed. This means promotion can never silently substitute a newer map for the one the user reviewed.

This promotion is intentionally not yet wired into `analysis/shared_timeline.json` or arrangement export. Bass, Lead, and Rhythm therefore do not consume the reviewed map until the next integration slice explicitly connects this promoted authority to the shared-timeline consumer path. Existing automatic shared-timing promotion remains separate in the meantime.

All existing source-rights, score-mapping, source-acceptance, tone, packaging, live Rocksmith, and NoCableLauncher boundaries remain unchanged. No commercial audio, tab content, private CFSM exports, or Ubisoft-derived material belongs in repository fixtures.
